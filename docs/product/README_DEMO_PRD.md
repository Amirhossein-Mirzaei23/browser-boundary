## Problem Statement

A prospective user cannot verify the package's central promise from the README. The page describes real historical browser execution and shows an illustrative boundary, but it does not contain a recording, screenshot, or reproducible controlled target that proves:

1. a real historical browser binary was launched;
2. the requested, on-disk, and live runtime browser versions match;
3. one version passes and an older version fails for a known reason, using adjacent majors where available and otherwise the nearest valid boundary pair;
4. the resulting boundary and evidence report were generated by `browser-boundary`.

This creates a trust gap before installation and makes the package harder to explain, evaluate, and share.

## Product Goal

Add a concise, trustworthy, and reproducible README demo that allows a new user to understand the product's value in under one minute and allows a maintainer to regenerate every committed demo artifact from repository sources.

## User Story

As a developer evaluating `browser-boundary`, I want to see a real historical browser cross a controlled compatibility boundary so that I can trust the package's core claim before installing it in my project.

## Demo Concept

Create a tiny local HTTP demo application with a deterministic browser-version boundary. The page must expose visible browser identity and use a feature known to be unsupported below a selected Chromium major. The selected boundary must be validated by real execution during implementation; it must not be chosen only from static compatibility tables.

The demo should produce:

- a passing result on the selected Chromium major;
- a failing result on the adjacent older major where available, or otherwise the nearest older major that can be validly acquired, launched, identity-verified, and tested;
- a visible runtime browser version or user-agent string in the page or captured browser UI;
- a generated compatibility report showing `oldestVerifiedPassing` and `firstVerifiedFailing`;
- a short terminal recording or animated image showing the command and final result.

If the adjacent historical artifact is unavailable or cannot be validly launched on the capture host, use the nearest valid older failing version and disclose the unverified gap. Never convert an unavailable version into a failure, and never describe a non-adjacent pair as proof that the exact transition occurred between consecutive majors.

## Proof Hierarchy

The demo must establish four levels of proof in order. A later level is invalid unless all earlier levels are satisfied.

### Level 1 — Execution proof

Prove that the resolved historical browser executable actually launched and created the automation session used for the scan. A downloaded archive, executable path, process log, or browser window alone is insufficient; the evidence must connect the launched process/session to the tested run.

### Level 2 — Identity proof

Prove independently of requested-version metadata that the launched browser is the claimed engine and major. Identity verification must use both:

1. **on-disk identity:** invoke the resolved browser executable's version command or equivalent trusted binary inspection and parse its reported engine/version; and
2. **live-session identity:** query the running automation session through the controller or browser protocol, such as WebDriver session capabilities (`browserName` and `browserVersion`), Playwright `browser.version()`, or Chromium `Browser.getVersion`.

For a real-major result, the requested major, on-disk reported major, and live-session reported major must agree. The engine identities must also agree. A mismatch, missing live-session value, or unparsable value makes that version `inconclusive` for the canonical demo.

The demo page may display `navigator.userAgent` or another browser-visible value to help viewers understand the recording, but page-controlled User-Agent text is presentation evidence only. It must not be the independent source of truth because it can be overridden or spoofed. Build labels, archive filenames, requested-version arguments, and cache-directory names are also not sufficient identity proof.

The generated evidence should retain the requested version, on-disk reported version, live runtime version, identity-verification method, engine, controller, and mismatch reason when verification fails.

### Level 3 — Compatibility proof

After identity is verified, prove that the controlled application passes in the newer tested version and fails in the older tested version because of the selected compatibility break. The failure must come from observed runtime behavior and the configured checks, not from browser acquisition, launch, driver, network, or host infrastructure.

### Level 4 — Detection proof

Prove that `browser-boundary` correctly classifies the two compatibility outcomes, derives the documented boundary semantics, and writes terminal and generated-report evidence that agrees with the raw run. Manually inferred or edited boundary values do not satisfy this level.

## Exact Boundary Semantics

The canonical demo uses two identity-verified evidence points for one engine:

- `P`: the oldest tested major in the demo that produces a verified `pass`;
- `F`: the newest tested major older than `P` that produces a verified compatibility `fail`.

The demo may report:

- `oldestVerifiedPassing = P`; and
- `firstVerifiedFailing = F`.

These names describe observed evidence points, not a claim about every untested major.

The boundary classification is:

1. **Exact adjacent boundary:** `P = F + 1`. The demo may state that the observed transition is between `F` and `P` for the controlled application, routes, checks, and capture environment.
2. **Non-adjacent verified boundary bracket:** `P > F + 1` because one or more intervening majors are unavailable, unlaunchable, inconclusive, or not valid candidates. The demo must state `verified FAIL at F; verified PASS at P; versions F+1…P-1 unverified/inconclusive as applicable`. It must not claim the exact transition major.
3. **No verified boundary:** either side lacks identity-verified compatibility evidence, the older result is infrastructure-only/inconclusive, the newer result does not pass, or contradictory tested outcomes make the selected monotonic boundary interpretation invalid. The capture workflow must fail rather than publish a boundary.

Only a compatibility `fail` can establish `F`. `inconclusive`, `error`, `skipped`, missing, and identity-mismatch outcomes never establish the failing side. The demo proves behavior only for its controlled application, configured route(s), checks, browser artifacts, controller, OS, architecture, and recorded environment. It does not establish a universal browser support claim.

## Functional Requirements

### FR1: Controlled local target

Add a small demo target under `examples/readme-demo/` or another repository-local example directory.

The target must:

- run without an external service;
- listen on localhost using an ephemeral or documented port;
- render a clear success state when the selected feature works;
- produce a deterministic compatibility failure when the selected feature is unsupported;
- display browser identity in a human-readable way;
- avoid analytics, external fonts, remote scripts, and network dependencies;
- shut down cleanly after capture or verification.

### FR2: Real historical browser verification

Run the demo through the actual `browser-boundary` CLI using historical Chromium binaries.

The implementation must verify:

- the on-disk browser identity and independently queried live-session identity both match the requested engine and major;
- page-visible User-Agent/version text is treated as presentation evidence, not the identity authority;
- at least one real version passes;
- at least one real older version fails;
- the passing and failing versions are adjacent where available, otherwise the nearest valid pair is used and the intervening gap is disclosed;
- unavailable or unlaunchable versions remain inconclusive;
- the generated report attributes the result to observed runtime behavior rather than a spoofed identity.

### FR3: Reproducible capture workflow

Add a script, documented command sequence, or both that:

1. starts the local demo server;
2. waits until it is ready;
3. runs the built package or source CLI against the demo;
4. writes temporary reports outside committed source paths;
5. captures the terminal demonstration;
6. extracts or copies only the approved README assets;
7. cleans up the server and temporary reports.

The workflow must fail if the expected pass/fail boundary is not observed.
It must also fail if either evidence point lacks execution proof, independent identity proof, compatibility proof, or matching detection/report proof.

### FR4: README integration

Replace the existing TODO near the result section with a “See it find a real boundary” demo section.

The section must contain:

- the terminal recording or animated image;
- concise alt text that states what is shown;
- the exact reproducible command;
- the observed browser versions and boundary;
- a link to the local demo source;
- a link to capture/regeneration instructions;
- a note that the result belongs to the controlled demo and is not a universal website compatibility claim.

The demo must appear before the long CLI reference and troubleshooting sections.

### FR5: Static fallback

Provide a useful experience when animation is disabled or unsupported.

Include at least one of:

- a static screenshot of the historical browser and result;
- an adjacent text transcript containing the key boundary;
- a compact generated Markdown report excerpt.

### FR6: Asset management

Store durable README assets in a dedicated path such as `docs/assets/readme-demo/`.

Requirements:

- use relative repository URLs from the README;
- keep the recording short and optimized for GitHub rendering;
- do not include secrets, usernames, home-directory paths, unrelated windows, or machine-specific tokens;
- do not commit raw browser traces or large temporary report directories;
- document the command and environment used to regenerate assets.

### FR7: Documentation consistency

Update relevant documentation so that:

- the quick start and demo commands agree with actual CLI behavior;
- illustrative values are not presented as observed demo values;
- WebKit is not described as Safari;
- historical version failures caused by infrastructure remain inconclusive;
- the demo's tested OS, architecture, Node.js version, package version, and Playwright version are recorded with the capture instructions.

## Recommended Demo Flow

The README should communicate this sequence:

1. A controlled local page is started.
2. `browser-boundary` launches a real older Chromium build.
3. The executable identity and live automation session independently identify the running browser; the page displays identity for the viewer without serving as the authority.
4. The compatible version passes.
5. The adjacent incompatible version fails on the selected feature where available; otherwise the nearest valid older version fails and the gap is disclosed.
6. The terminal prints either an exact adjacent boundary or a non-adjacent verified boundary bracket using the defined semantics.
7. The report excerpt shows the same execution, identity, compatibility, and detection evidence.

Keep the visible recording focused on the result. Browser download progress may be omitted from the primary recording if the capture instructions explicitly state that required binaries were already cached.

## Risks and Mitigations

### Historical artifacts disappear

Mitigation: Document exact tested versions and allow maintainers to select the nearest valid boundary pair. Prefer adjacent majors, but disclose any gap and report a verified bracket rather than an exact transition. The verification workflow must reject unavailable versions rather than mislabel them.

### Demo becomes flaky

Mitigation: Use localhost-only resources, explicit readiness selectors, deterministic content, bounded startup waits, and no third-party requests.

### Recording becomes stale after CLI output changes

Mitigation: Provide one regeneration command and keep the underlying JSON verification independent of visual capture.

### Asset is too large

Mitigation: Keep the recording short, crop to relevant content, reduce dimensions and frame rate, and include a lightweight static fallback.

### Demo overstates platform support

Mitigation: Record the capture environment and describe only the tested Chromium behavior. Keep platform and WebKit limitations visible.
